## 1. 技术栈选型说明

### 1.1 选型总表

| 层次 | 选型 | 版本 | 选型理由 |
| --- | --- | --- | --- |
| 运行时 | Node.js | **≥ 22.5**（LTS） | 前后端同语言，单进程常驻内存低，2GB 服务器友好；**使用内置 `node:sqlite` 要求 ≥ 22.5** |
| 后端框架 | **Fastify** | 4.x | 相比 Express 更低的开销与更快序列化；内置 JSON Schema 校验（ajv）与 pino 日志，减少依赖引入；插件式静态资源托管 |
| 数据库 | **SQLite** | 3.40+ | 无独立服务进程、零网络开销、单文件备份；详见 4.1 选型对比 |
| 数据库驱动 | **Node 内置 `node:sqlite`** | Node 22.5+ | **零原生依赖、免编译**（`DatabaseSync` 同步 API）；无连接池与回调开销；配合 WAL 满足单用户并发 |
| 参数校验 | Fastify JSON Schema | — | 框架内置，无需额外库，且能显著加速请求序列化 |
| 鉴权 | **无（应用内不做鉴权）** | — | 单用户自用工具，打开即用；如需限制公网访问由部署层承担（见 7.5） |
| 前端框架 | **Vue 3** | 3.5.x | 体积小、学习成本低、单页应用足够；不引入重量级 UI 组件库 |
| 构建工具 | **Vite** | 5.x | 构建产物小、支持按需打包与 gzip/brotli 预压缩 |
| 图表库 | **Apache ECharts** | 5.x | 折线/多系列/断点/**反向 Y 轴（排名）**/响应式能力完整；**按需引入**控制体积 |
| 状态管理 | Pinia | 2.x | 官方推荐，轻量 |
| HTTP 客户端 | axios | 1.x | 统一拦截器（错误码统一处理）；无需 Token 注入 |
| 样式方案 | 原生 CSS + CSS 变量 + 媒体查询 | — | 避免 Tailwind/Element Plus 带来的体积与学习成本；断点式响应式足够满足 Web/移动双端 |
| 日志 | pino（Fastify 内置） + 按日轮转 | — | 结构化日志、低开销；轮转限制磁盘增长 |
| 进程守护 | systemd（主） / PM2（备选） | — | systemd 零额外内存；PM2 便于 `max_memory_restart` 配置 |
| 反向代理 | Nginx（可选） | — | 需要 HTTPS/域名/静态资源缓存时启用；否则由 Fastify 直接托管静态资源以省内存 |
| 测试 | Vitest（单元） + 接口冒烟脚本 | — | 覆盖派生指标计算、科目匹配、AI 结果解析、目标差距计算等纯函数逻辑 |
| 版本管理 | Git | — | 常规 |

### 1.2 关键选型决策与取舍记录

| 决策点 | 备选 | 结论 | 理由 |
| --- | --- | --- | --- |
| 后端框架 | Express vs Fastify vs NestJS | **Fastify** | Express 无内置校验与日志，需额外依赖；NestJS 抽象重、启动内存更高，对单用户应用属过度设计 |
| 数据库驱动 | better-sqlite3 vs node:sqlite（Node 内置） vs sqlite3 CLI | **node:sqlite（Node 内置）** | 免原生编译（部署环境无法拉取 Node headers 时 better-sqlite3 无法安装）；同步 API、零依赖、内存占用低；事务语义由 `db/transaction()` 封装提供 |
| 数据库 | SQLite vs MySQL vs PostgreSQL | **SQLite** | 见 4.1 |
| ORM | 裸 SQL vs Prisma vs Knex | **裸 SQL + 轻量 DAO 层** | 表数量少（10 张）、查询以聚合为主，ORM 带来的体积、内存与启动开销不划算；裸 SQL 便于精确优化统计查询 |
| 前端 UI 库 | Element Plus vs 原生 CSS | **原生 CSS** | 移动端适配可用 CSS 变量 + 媒体查询廉价实现；省去约 300KB+ 体积，利于 NFR-4 |
| 鉴权方案 | JWT 登录 vs 无鉴权 | **无鉴权** | 按用户要求"打开即可看到主页面"，省去鉴权中间件、Token 存储与口令安全成本 |
| 满分口径 | 每次满分快照 vs 固定中考满分 | **固定中考满分（总分 730）** | 按用户要求"满分定死"，简化数据结构（删除 `exam_score.full_score`），并与目标院校录取线口径天然可比 |
| 比较口径 | 得分率 vs 原始分 | **原始分** | 满分已固定，跨考试满分一致，无需得分率；同时移除该指标的所有计算与展示 |
| 是否引入 Nginx | 引入 vs 不引入 | **默认不引入** | 省一份进程内存；仅在绑定域名/HTTPS 时引入 |
| 是否多进程 | cluster vs 单进程 | **单进程** | 内存约束优先；单用户负载下 2 核完全够用，多进程反而放大内存 |

## 2. 系统架构与部署拓扑

### 2.1 逻辑架构

> 说明：**无鉴权中间件、无 Token 校验**，请求直连业务路由。

### 2.2 部署拓扑（默认，无 Nginx）

```
公网 ──► 80/443 ──► Node.js (Fastify, systemd 守护)
                     ├─ /            → 静态资源 dist/
                     ├─ /api/v1/*    → REST 接口
                     └─ 监听 127.0.0.1 或 0.0.0.0:3000
```

启用 Nginx 时的拓扑：

```
公网 ──► Nginx (443, TLS 终结, gzip/br, 静态缓存)
           ├─ /          → 直接返回 dist/ 静态文件（root）
           └─ /api/v1/   → proxy_pass 到 127.0.0.1:3000
```

> 选择原则：**无域名/无证书需求时不要引入 Nginx**，用 `@fastify/static` + `@fastify/compress` 即可满足 gzip 与静态托管，可节省约 10–20MB 常驻内存与一份配置维护成本。若需限制公网访问（应用无鉴权），应在部署层处理：绑定 `127.0.0.1` + SSH 隧道、内网访问、或 Nginx IP 白名单 / Basic Auth。

### 3.2 编码规范约定

- **纯函数优先**：所有派生指标（总分、Δ、均值、连续下滑、名次进退、中考口径总分、目标差距）实现为 `server/src/lib/metrics.js` 中的纯函数，前后端共用同一口径定义；前端不得自行实现另一套计算。
- **事务边界明确**：凡涉及多次写入（建考试+写成绩+写排名、批量导入、覆盖恢复）必须包在 `db.transaction()` 中。
- **接口分层**：路由层只做校验与调用服务层；服务层不做 HTTP 相关处理。
- **命名**：数据库字段 `snake_case`，JS 变量 `camelCase`，接口路径 `kebab-case` 复数资源。
- **时间**：数据库统一 `YYYY-MM-DD` 与 ISO 8601 UTC+08 语义；禁止直接存时间戳用于业务日期。
- **无重复口径**：趋势图与 AI 分析必须共享同一份统计摘要构造逻辑（`statsService.buildSummary()`）。
- **满分约束**：科目满分与总分满分（730）为常量，禁止在业务代码中出现"每次考试满分"的概念；得分上限校验一律对照科目字典。

## 4. 数据库选型及设计方案

### 4.1 选型对比与结论

| 方案 | 独立进程 | 内存占用 | 单用户读写性能 | 备份/迁移 | 运维复杂度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **SQLite + WAL** | 否 | ~几 MB（含页缓存可限） | 极佳（本地文件、无网络往返） | 单文件复制 / `.backup` 热备 | 极低 | **采用** |
| MySQL 8 | 是 | 300–500MB+ | 好 | mysqldump | 中（需守护、调参、占用内存） | 否，2GB 内存下性价比低 |
| PostgreSQL | 是 | 200–400MB+ | 好 | pg_dump | 中 | 否，同上 |
| LevelDB/LMDB 纯 KV | 否 | 低 | 好 | 文件复制 | 低 | 否，缺乏关系查询与聚合能力，统计需全量扫描 |
| 纯 JSON 文件 | 否 | 低 | 差（每次全量读写） | 文件复制 | 极低 | 否，无事务与并发安全，统计需内存全量加载 |

**结论：SQLite + WAL 模式。** 依据：

1. 数据规模极小（一年半约 700 条成绩记录，见产品文档 NFR-11），SQLite 的性能上限远超需求。
2. 单用户场景不存在写并发争抢，WAL 的"单写多读"特性足够；无写锁阻塞风险。
3. **不引入独立数据库进程**可直接省下 200–500MB 常驻内存，对 2GB 服务器是决定性优势。
4. 单文件 + `.backup` 命令即可实现一致性的热备份，40GB 磁盘下可轻松保留大量历史备份。

### 4.2 连接与 PRAGMA 调优（每次连接建立后执行）

```sql
PRAGMA journal_mode = WAL;        -- 读写并发，避免写时阻塞读
PRAGMA foreign_keys = ON;         -- 开启外键约束
PRAGMA synchronous = NORMAL;      -- WAL 下兼顾安全与性能（不设为 FULL，避免每事务 fsync 抖动）
PRAGMA busy_timeout = 5000;       -- 写锁等待 5s，避免 SQLITE_BUSY 直接失败
PRAGMA cache_size = -8000;        -- 页缓存约 8MB，防止占用过多内存
PRAGMA temp_store = MEMORY;       -- 临时表放内存，减少磁盘 IO
PRAGMA mmap_size = 134217728;     -- 128MB 内存映射上限（按需调低）
PRAGMA auto_vacuum = INCREMENTAL; -- 抑制文件无限增长
```

> `mmap_size` 与 `cache_size` 是内存预算的关键调节旋钮；若实测 RSS 偏高，优先下调这两个值。
> 上述 PRAGMA 通过 `node:sqlite` 的 `DatabaseSync.exec()` 在每次建立连接后立即执行（见 `server/src/db/index.js`）；事务由 `db/transaction()` 封装（`BEGIN` / `COMMIT` / 异常 `ROLLBACK`）。

### 4.4 视图：考试汇总（避免冗余字段不一致）

总分等派生值**不落库为冗余列**，改用视图计算，规避并发写入导致的不一致与手工同步成本。数据量下视图性能无压力。

```sql
-- v1.2：满分改为按考试学段从 subject_grade 取，进入总分判定同样按学段
CREATE VIEW v_exam_summary AS
SELECT
  e.id                                        AS exam_id,
  e.name                                      AS name,
  e.exam_type                                 AS exam_type,
  e.exam_date                                 AS exam_date,
  e.grade                                     AS grade,
  e.term                                      AS term,
  e.status                                    AS status,
  e.source                                    AS source,
  e.class_rank                                AS class_rank,
  e.class_size                                AS class_size,
  e.grade_rank                                AS grade_rank,
  e.grade_size                                AS grade_size,
  COUNT(s.id)                                 AS entered_subject_count,
  COALESCE(SUM(CASE WHEN COALESCE(sg.counts_to_total, sub.counts_to_total) = 1
                     AND s.is_absent = 0
                    THEN s.score END), 0)     AS total_score,
  COALESCE(SUM(CASE WHEN COALESCE(sg.counts_to_total, sub.counts_to_total) = 1
                     AND s.is_absent = 0
                    THEN COALESCE(sg.full_score, sub.full_score) END), 0)
                                              AS entered_full_score
FROM exam e
LEFT JOIN exam_score    s   ON s.exam_id   = e.id
LEFT JOIN subject       sub ON sub.id      = s.subject_id
LEFT JOIN subject_grade sg  ON sg.subject_id = s.subject_id AND sg.grade = e.grade
GROUP BY e.id;
```

### 4.6 迁移与备份方案

**迁移：**
- 采用**顺序编号 SQL 文件 + `schema_version` 表**驱动，启动时自动执行未应用的迁移。
- 迁移文件只允许"新增"，禁止修改已发布的迁移文件。
- **每个迁移文件末尾必须自带 `INSERT OR IGNORE INTO schema_version (version, description) VALUES (N, '...')`**——迁移器以 `schema_version` 判断是否已应用，漏登记会导致下次启动**重放该文件**（如迁移 003 曾因漏写而重复 `ALTER TABLE ... ADD COLUMN`，报 `duplicate column name: line_mode` 致服务启动失败）。修复办法是在文件末尾补登记并把版本行手工补登入库。
- 每个迁移在单个事务内执行；执行前自动生成一次 DB 文件快照（`data/studylog.db.bak.{version}`）。
- 迁移器在应用启动流程中同步执行，失败则**拒绝启动**并输出明确错误（避免带病运行）。
- **恢复快照的注意事项**：停服后除 `cp data/studylog.db.bak.NNN data/studylog.db` 外，必须同时删除 `data/studylog.db-wal` 与 `data/studylog.db-shm`，否则残留 WAL 会在启动时回放，把已撤销的列/数据带回，导致"恢复无效"。
- **执行迁移的工作目录**：必须从仓库根执行 `node server/src/db/migrate.js`。若用 `npm --prefix server run migrate`，`cwd` 变为 `server/`，迁移会落到游离的 `server/data/studylog.db`（线上库不受影响，易造成"迁移成功但界面无变化"的误判）。

**备份：**
- 每日 03:00 执行 `sqlite3 .backup`（热备，不阻塞读写），输出 `backups/studylog-YYYYMMDD.db`。
- 保留最近 `BACKUP_RETAIN_COUNT`（默认 30）份，超出按时间最旧删除。
- 应用内提供"导出全量 JSON"作为可读归档；导入为**覆盖式恢复**，执行前先生成一次快照。
- 备份文件不进入 Git（`.gitignore` 排除 `data/`、`backups/`、`logs/`、`.env`）。

## 6. 大模型 API 集成方案

### 6.1 用途与边界

| 能力 | 输入 | 输出 | 模型依赖 | 失败影响 |
| --- | --- | --- | --- | --- |
| 成绩文本解析 | 用户粘贴的原始文本（≤ 2000 字） | 严格 JSON：考试信息 + 科目得分项 + 排名 + 告警 | 强依赖（无 AI 不可用） | 降级为手动录入，业务可继续 |
| 学情分析 | M5 已计算的结构化摘要（非原始成绩表） | 固定小节的结构化结论 + Markdown 正文 | 强依赖 | 降级为规则分析（`isFallback=1`） |

**设计铁律：**
1. **AI 不直接写库。** 解析结果必须先返回前端、经用户校对，再由 `/ai/parse-score/commit` 以校对后的数据入库。服务端复核所有约束。
2. **AI 不产生数字。** 学情分析的所有分数、Δ 值、均值差、名次、目标差距均来自传入的结构化摘要；提示词中明确禁止编造数据，并要求引用给定数值。
3. **AI 不可用时不得阻断主流程。** 两条能力均需有降级路径。
4. **AI 配置仅来自 `.env`**（默认 `AI_PROVIDER=deepseek`），无数据库覆盖、无前端配置。

### 6.2 接口调用约定

- 协议：`POST {AI_BASE_URL}/chat/completions`（OpenAI 兼容）
- 超时：`AI_TIMEOUT_MS`（默认 20000ms），使用 `AbortController`
- 重试：仅对网络错误与 5xx 重试 1 次，指数退避（500ms → 1500ms）；**不重试** 4xx（含额度与鉴权问题）
- 输出约束：优先使用 `response_format: { type: "json_object" }`；服务端仍必须对返回内容做 JSON 提取与 schema 校验（剥离 ```json 代码块围栏、容忍前后缀噪声）
- 温度：解析 `temperature = 0`；分析 `temperature = 0.3`
- `max_tokens`：解析 4000；分析 12000（可由 `AI_MAX_TOKENS_PARSE` / `AI_MAX_TOKENS_ANALYSIS` 覆盖）
  - **注意（实测踩坑）**：推理型模型（如 `deepseek-flash`）会先输出 `reasoning_content` 并计入 completion token（实测 1.3k–4k+）。预算配置过小会把 JSON 输出截断甚至导致 `content` 为空（`finish_reason=length`）。服务端在 `content` 为空时抛出**明确的 3001 错误并提示调大预算**，且 `extractJson` 内置截断修复兜底。`reasoning_effort` / `effort` 参数实测**不被该端点采纳**，只能通过加大 token 预算解决。
- 成本控制：输入为压缩后的摘要文本（数百 token 量级）；`ai_parse_task.token_usage` 记录用量便于观察
- **启动自检**：进程启动时可做一次轻量连通性探测（不设置 API Key 时跳过），结果仅写日志；`/ai/status` 只暴露 `configured/provider/model` 布尔与名称。

### 6.3 提示词设计要点

**解析（System 提示词结构）**

```
你是成绩单结构化助手。请从用户提供的文本中提取考试信息、各科成绩与名次。
硬性要求：
1. 只输出 JSON，不要任何解释文字。
2. 科目名保持原文（rawSubject），不要自行改写成标准名。
3. 分数必须是文本中出现的原始数字；不要推断、不要补全、不要计算满分。
4. 等级类成绩（如 A/B/C/D、优良中差）填入 gradeLevel。
5. 若文本中出现班级/年级排名与人数，填入 ranks；没有则为 null。
6. 无法确定的内容放入 warnings，不要猜测。
输出结构：
{"exam":{"name":..,"examDate":"YYYY-MM-DD","examType":{"unit|week|month|midterm|final|mock|sport|lab|other"}},
 "items":[{"rawSubject":"..","score":number|null,"gradeLevel":"A|B|C|D"|null}],
 "ranks":{"classRank":number|null,"classSize":number|null,"gradeRank":number|null,"gradeSize":number|null},
 "warnings":[{"level":"warn|info","message":".."}]}
```

> 关键点：让模型"只做提取、不做推断"，把不确定内容显式暴露为 `warnings`。**满分的补全由服务端规则完成**（按科目字典预填中考满分），而非交给模型猜，从而保证可解释与可校验。

**分析（System 提示词结构）**

```
你是初中学生学习顾问。基于给定的结构化成绩摘要输出学情分析。
硬性要求：
1. 所有数值必须直接引用摘要中的数字，禁止编造或推算新数字。
2. 只使用摘要中提供的信息（含排名趋势与目标院校差距），不得引入外部数据。
3. 结论需可执行：建议必须具体到"做什么、怎么做"，避免"多努力"这类空话。
4. 只输出 JSON：{"overall":"..","strengths":[".."],"weaknesses":[".."],
   "trend":"..","rankTrend":"..","targetGap":"..","suggestions":[".."]}
5. 报告是给学生和家长阅读的中文报告，正文必须全部使用中文。严禁出现英文单词、
   英文字段名或英文缩写（例如 classDelta、status、gap、myTotal、below、
   above、null）。
6. 不得输出 HTML 标签或 Markdown 代码（例如 <div>、<th>、```）。
7. 某项数据为"暂无数据"时，用中文说明缺少该项数据，不要照写 null。
```

> **实测踩坑（v1.1-B 修复）：** 早期版本直接把 `buildSummary()` 的英文键结构 JSON 交给模型，模型会在正文里原样回显字段名（出现"`classDelta` 为 3""`status below`""`gap 45.7`"这类词）。修复方式为双保险：① 调用前用 `toChineseSummary()` 把摘要**投影为中文键**（`排名趋势.班级名次进步数`、`目标院校对比.各校[].与录取线对比` = "我的总分低于录取线" 等）再序列化；② System 提示词补充第 5–7 条中文约束。修复后同一范围重复生成，报告正文的拉丁字母出现次数为 0（实测断言：`match(/[A-Za-z]+/g)` 无命中）。

摘要构造（`statsService.buildSummary()`）包含：考试列表与日期、总分序列、各科分数序列、各科 Δ得分、各科 vs 均值差、连续下滑科目、缺考与未录入科目清单、**班级/年级排名序列与名次进退**、**目标院校录取线与差距/提分空间**。投喂模型时经 `toChineseSummary()` 转换为中文键结构，键值含义一一对应，不改变任何数值。

### 6.4 科目名匹配算法（纯函数，`lib/subjectMatch.js`）

按优先级依次尝试：

1. **精确匹配**：`rawSubject` 去空格后与 `subject.name` 或 `subject.code` 完全相等 → `exact`
2. **别名匹配**：命中 `app_config.subject_alias` 中的别名数组 → `alias`
3. **归一化匹配**：去除"科""科目""成绩"等后缀与全半角差异后再比对 → `fuzzy`
4. **包含匹配**：字典名与 `rawSubject` 互为子串 → `fuzzy`
5. **未命中**：`unmatched`，前端高亮并要求用户手动选择科目或删除该行

> 该函数必须配套单元测试：覆盖别名、后缀噪声、全半角、拼音缩写、错别字临近匹配等用例；`fuzzy` 与 `unmatched` 一律不得自动入库。

### 6.5 目标差距计算（纯函数，`lib/schoolCompare.js`）

- **基准总分**：
  - `latestPerSubject`（默认）：遍历所有 `counts_to_total=1` 的科目，取该科目在已确认考试中**最近一次非缺考**的得分，求和；从未录入的科目记入 `missingSubjects` 并按 0 计入总分。
  - `examId=<id>`：取该次考试的 `total_score`。
- **录取线取值**：`avg3y` = 有数据的最近 3 个年度的算术平均；`latest` = 最近一年。
- **跨口径折算**：若 `total_full_score ≠ 730`，先折算：`折算线 = min_score / total_full_score × 730`，再参与比较。
- **差距**：`gap = 录取线 − 基准总分`（负=需提分，正=已超线）。
- 该函数必须配套单元测试：含"未录入科目"、"口径不一致折算"、"跨年缺年"等边界用例。

### 6.6 结果缓存与降级

**缓存：**
- 输入指纹 `data_digest` = 摘要内容的 SHA-256 前 16 位。
- 生成分析前先查 `analysis_report.data_digest`，若 24 小时内存在同指纹且非兜底报告，直接复用并提示"该范围内数据未变化，已复用最近报告"。

**降级规则分析（`lib/ruleAnalysis.js`）：**
- 低于均值最多的 2 科 → 薄弱
- 高于均值最多的 2 科 → 优势
- `scoreDelta <= -1` 的科目 → 退步
- 连续下滑 ≥ 阈值（默认 3）的科目 → 重点预警
- 名次持续退步（年级排名连续下降）→ 排名预警
- 距目标院校差距最大的一所 → 目标提示
- 波动最大（分数标准差最大）的科目 → 稳定性提示
- 输出结构与 AI 报告一致，`is_fallback=1`，前端展示"基础分析（规则生成）"标识

**降级触发条件：** 未配置 API Key、连续两次调用失败、超时、额度错误（3003）。降级必须**在响应中显式标注**，不得静默伪装成 AI 报告。

## 7. 线上低配置环境适配方案

### 7.1 资源预算核算

服务器：2 核 vCPU / 2GB 内存 / 40GB 存储。

| 项目 | 预算 | 说明 |
| --- | --- | --- |
| OS 基础占用 | ~250MB | 精简发行版实测通常 150–350MB |
| Node.js 进程 RSS | 150–250MB | 通过 `--max-old-space-size` 上限约束 |
| SQLite 页缓存 | ≤ 8MB | `cache_size = -8000` |
| SQLite mmap | ≤ 128MB（虚拟映射） | 可按内存压力下调 |
| Nginx | 0 或 ~10MB | 默认不部署 |
| **内存合计** | **~450–520MB** | 占 2GB 的 25% 左右，余量充足 |
| 代码 + node_modules | ~300–450MB | 生产环境仅装 dependencies |
| SQLite 数据库 | < 20MB | 700 条成绩记录的极小规模 |
| 备份文件 | ≤ 30 × 5MB ≈ 150MB | 按保留 30 份估算 |
| 日志 | ≤ 100MB | 14 天保留 |
| **磁盘合计** | **< 1GB** | 占 40GB 的 2.5% |
| CPU | 单用户负载极低 | 主要消耗在两处：SQL 聚合（毫秒级）与 AI 外呼（IO 等待，不占 CPU） |

**结论：本方案在 2 核 2GB / 40GB 环境下有显著余量，无需牺牲功能。**

### 7.2 内存适配措施（必做项）

| 措施 | 具体做法 |
| --- | --- |
| 进程堆上限 | 启动参数 `node --max-old-space-size=384 server.js`，留出 OS 与其它进程空间 |
| 单进程运行 | 禁用 `cluster`，不做多实例；2 核在单用户负载下无瓶颈 |
| SQLite 缓存限制 | `cache_size = -8000`（约 8MB）；不用默认的 2000 页大缓存 |
| 避免全量加载 | 统计接口一律 SQL 聚合，禁止把全部成绩 `SELECT *` 后进内存再算 |
| 分页与 LIMIT | 列表接口强制分页；矩阵接口限制单页最大行数 |
| 流式导出 | 导出大数据时使用流式写响应（`Readable` + `.iterate()`），避免一次性构造大对象 |
| AI 结果不驻留 | 解析任务 `parsed_json` 落库，不在内存中长期缓存 |
| 定期观察 | 用 `process.memoryUsage()` 暴露到 `/health` 中 RSS 字段，便于外部监控 |

### 7.3 磁盘适配措施

| 措施 | 具体做法 |
| --- | --- |
| 日志轮转 | pino 写文件 + 按天切割（`pino-roll` 或 `logrotate`），保留 `LOG_RETAIN_DAYS`（默认 14）天 |
| 禁止日志打印全量 body | 生产日志级别 `info`；请求体只记录长度与关键字段，避免成绩文本反复落盘 |
| 备份滚动 | 保留 30 份，超出自动删除最旧 |
| SQLite 膨胀控制 | `auto_vacuum = INCREMENTAL`，定期执行 `PRAGMA incremental_vacuum` |
| WAL 文件控制 | 定时（如每小时）触发一次 `PRAGMA wal_checkpoint(TRUNCATE)`，避免 WAL 无限增长 |
| 磁盘水位告警 | 启动/定时检查剩余空间，低于 10% 时在日志中输出 `warn` |

### 7.4 前端体积与网络适配

| 措施 | 具体做法 |
| --- | --- |
| 图表按需引入 | ECharts 使用 `echarts/core` + 仅注册折线图、坐标轴、tooltip、legend、dataZoom、canvas 渲染器；排名图复用同一折线组件（`yAxis.inverse=true`） |
| 样式零框架 | 使用原生 CSS + CSS 变量；不引入 UI 组件库 |
| 构建压缩 | Vite 开启 `build.minify`，产物启用 gzip（`@fastify/compress` 或构建期预压缩 `.gz`） |
| 资源缓存 | 静态文件名带内容 hash，`Cache-Control: public, max-age=31536000, immutable`；`index.html` 不缓存 |
| 代码分割 | 路由级懒加载，图表页独立 chunk |
| 首屏预算 | gzip 后 JS + CSS < 300KB（NFR-4 硬指标，构建产物需在 CI/本地核对） |
| 移动端优化 | 图表实例在移动端减少数据点密度（如超过 50 点时按需抽稀）、关闭动画以降低开销 |

### 7.5 部署与运维配置

**项目运维脚本（`studylog.sh`，适用于未启用 systemd 的开发/单机直跑场景）：**

```bash
./studylog.sh start      # 后台常驻启动；写入 data/studylog.pid，日志追加到 logs/app.log
./studylog.sh stop       # 先 SIGTERM 优雅退出（等 15s），超时改 SIGKILL
./studylog.sh restart    # 等价于 stop + start
./studylog.sh status     # 运行状态 / PID / 常驻内存 / 健康检查结果（未运行返回码 1）
./studylog.sh log 100    # 查看最近 100 行日志
```

**日常重启脚本（`restart.sh`）——改完代码一键生效：**

```bash
./restart.sh            # 构建前端 → 重启服务 → 健康检查（失败则以非 0 退出）
./restart.sh --no-build # 仅改了服务端代码时跳过前端构建，重启更快
./restart.sh --help
```

`restart.sh` 是 `studylog.sh` 之上的薄封装，之所以**默认先构建再重启**：Fastify 单进程同时提供 `/api/v1` 与 `web/dist` 静态页，前端改动不重新构建则不会生效（仅刷新浏览器不足以加载新产物）。构建失败时会**中止重启并保持服务原状**，避免把线上服务停在半成品产物上。若检测到服务由 systemd 托管（`systemctl is-active studylog`），则自动改用 `systemctl restart`，避免 PID 方式再拉起一个实例造成端口冲突。

设计要点：
- **PID 文件驱动，不使用 `pkill -f` 按名称匹配**——脚本自身命令行文本包含入口路径，按名称匹配会误杀执行脚本的 shell。
- 启动后**轮询 `/api/v1/health` 最多 20 秒**，健康检查通过才报告"启动成功"；进程提前退出则打印最近 20 行日志并以非 0 退出，便于接入 CI 或人工排查。
- 停止时先发 `SIGTERM` 走应用内的优雅退出（`server.js` 已监听并 `app.close()`），保证 WAL checkpoint 与连接收尾。
- `.env` 由应用自身加载，脚本仅从 `.env` 读取 `PORT`（默认 3000）与 `HOST`（`0.0.0.0` 时健康检查走 `127.0.0.1`）。
- 启动前会提示 Node 版本（需 ≥ 22.5）与 `web/dist` 是否已构建，避免"服务起来了但页面打不开"。
- `data/` 与 `logs/` 均已在 `.gitignore` 中，PID 与日志不会入库。
- **与 systemd 二选一**：生产用 `systemctl start studylog`，本地调试用 `./studylog.sh`，两者不要同时管理同一端口。

**systemd 单元（`deploy/studylog.service`）核心项：**

```ini
[Service]
Type=simple
WorkingDirectory=/root/studylog
EnvironmentFile=/root/studylog/.env
ExecStart=/usr/bin/node --max-old-space-size=384 server/src/server.js
Restart=always
RestartSec=3
MemoryMax=450M
StandardOutput=append:/root/studylog/logs/stdout.log
StandardError=append:/root/studylog/logs/stderr.log
```

说明：`MemoryMax=450M` 作为硬约束，一旦异常内存膨胀会被 cgroup 限制而非拖垮整机；`Restart=always` 实现自愈（对应 NFR-9）。未指定 `User=` 即以 root 运行，故代码置于 `/root/studylog`；若改为降权用户运行，需迁到 `/opt` 等 `0755` 路径，且不可启用 `ProtectHome=true`。

**健康检查：**
- `GET /api/v1/health` 返回 `{ status, dbReady, rssMb, uptimeSec, version }`，免鉴权。
- 外部探活（如 UptimeRobot）每 5 分钟探测，连续 2 次失败告警。

**定时任务（进程内，避免额外 cron 依赖）：**
| 任务 | 频率 | 说明 |
| --- | --- | --- |
| 数据库热备份 | 每日 03:00 | `.backup` + 滚动清理 |
| 日志轮转检查 | 每日 03:10 | 清理超期日志 |
| WAL checkpoint | 每小时 | `PRAGMA wal_checkpoint(TRUNCATE)` |
| 磁盘水位检查 | 每小时 | 低于阈值输出告警日志 |

**访问与安全措施（应用内不做鉴权）：**
- **无登录、无 Token、无口令**；打开即用（NFR-8）。
- 若需限制公网访问，采用部署层手段：`HOST=127.0.0.1` + SSH 隧道 / 内网访问；或在 Nginx 侧配置 IP 白名单 / Basic Auth / TLS。
- 响应头开启基础安全项：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`（由 `@fastify/helmet` 提供）。
- AI 密钥仅存于 `.env`，文件权限 `600`，不入 Git；日志中禁止打印密钥与完整请求头。

### 7.6 兼容性说明

- SQLite 由 **Node 内置 `node:sqlite`** 提供，**无需系统级安装数据库，也无需原生编译**，部署依赖进一步降低（vCPU 与内存均无额外开销）。
- **Node 需 ≥ 22.5**（`node:sqlite` 自 22.5.0 起提供）；部署前需固定版本（建议用 `nvm` 或发行版包管理），避免运行时差异。
- 不再依赖 better-sqlite3，也**不再需要 `python3` / `make` / `g++` 等编译链**；`node_modules` 不含原生模块，`npm install` 在受限网络环境下亦可完成。
- 浏览器兼容底线见产品文档 NFR-2；ECharts 5 与 Vue 3 均支持该范围。

### 8.2 执行顺序与并行策略

```
P0 工程底座
   └─► P1 数据层与配置（M1）           ← 口径地基，必须先冻结
          └─► P2 考试与成绩（M2+M3，含排名）
                 ├─► P3 统计与可视化（M5）   ← 接口契约需在 P2 结束前冻结
                 │      ├─► P4 智能批量录入（M4）
                 │      ├─► P5 智能学情分析（M6）
                 │      └─► P6 目标院校对比（M7）
                 └─► P7 低配适配与上线      ← 与 P4/P5/P6 可并行
                        └─► P8 打磨与验收
```

**并行可行性说明：**

| 可并行项 | 前提条件 | 说明 |
| --- | --- | --- |
| P3 前端图表开发 与 P4/P5/P6 后端开发 | 第 5 章接口契约冻结 | M5 为只读纯计算，可与 M4/M6/M7 并行；用固定的 mock 数据先行开发图表 |
| P6 与 P4/P5 | P3 完成 | 目标差距计算依赖 M5 总分口径，口径冻结后即可独立开发 |

### 8.4 开发过程中的口径纪律

以下几条是**最容易在实现中走样**的地方，作为开发纪律单独强调：

1. **满分按学段，不存快照、不算得分率。** 各科满分取**该学段**科目字典（`subject_grade`）中的满分，学段计入总分满分由字典推导（`gradeFullScore(grade)`：初二 570 / 初三 730）；得分上限一律对照该学段该科满分校验；任何位置不得出现"得分率"字段或计算，也不得再出现硬编码的 730 用于与"本次卷面满分"混用。
2. **两个"满分"概念不可混淆。** `enteredFullScore`（本次已录且计入总分科目的满分之和，如初三 10 月月考 600）用于"本次口径"展示与趋势参考线；`totalFullScore`（学段计入总分满分，初三 730）用于目标院校对比。同一页面同时出现时必须分别标注。
3. **跨学段不混算。** 总分趋势按学段分开；单科趋势仅在两学段满分相同时才允许混连（`grade=comparable`），历史等满分不同的科目必须排除。
4. **排名方向必须反向。** 排名数值越小越好，排名趋势图 Y 轴反向；名次进退用"进步/退步 N 名"表述（正=进步）。
5. **目标对比口径单一。** "中考口径总分"只有一份实现（`lib/schoolCompare.js`），且必须处理"未录入科目"与"跨年总分口径不一致折算"；该口径**仅适用于初三**。
6. **统计口径只有一份实现**（`server/src/lib/metrics.js`），图表与 AI 分析的输入摘要必须共用它，禁止前端或分析服务各写一套。
7. **无鉴权不等于无规范**：所有路由不再校验身份，但仍须做参数校验与错误统一包装，避免脏数据入库。

## 9. 风险清单与待确认事项

### 9.1 风险

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R-1 | 大模型解析准确率不稳定（幻觉、漏项、错配） | 写入错误成绩，污染趋势 | 强制人工校对环节 + 服务端约束复核 + `fuzzy/unmatched` 不入库 + 保留原始文本可回溯 |
| R-2 | 校内测试满分口径与学段字典不一致（如按 100 分卷） | 总分与趋势失真 | **满分按学段取科目字典值，页面固定提示当前学段与计入总分满分，请用户先折算再录入**；科目满分为只读常量，避免误改 |
| R-3 | 生物/地理等级制导致难以量化 | 折线口径混乱 | 等级科目不进入总分折线，独立展示等级序列 |
| R-4 | 郑州中招政策调整（科目/分值变化） | 默认口径失效 | 科目表可配置，不硬编码；政策变动时仅需更新配置与种子数据 |
| R-5 | 2GB 内存下 Node 进程被 OOM 杀掉 | 服务中断 | `--max-old-space-size` 与 systemd `MemoryMax` 双重约束 + `Restart=always` 自愈 + 定时观测 RSS |
| R-6 | AI 外呼费用累积 | 成本超预期 | 输入压缩为摘要、结果缓存复用、`token_usage` 记录观察、可关闭分析页面入口 |
| R-7 | ~~better-sqlite3 原生模块编译失败~~ **已消解**：改用 Node 内置 `node:sqlite` | 无 | 免编译、零依赖；仅要求 Node ≥ 22.5（见 7.6） |
| R-8 | **应用无鉴权，公网可直接访问数据** | 隐私泄露 | 默认绑定 `127.0.0.1` + 隧道/内网；或 Nginx 白名单/Basic Auth；部署文档明确"不加防护不要直接暴露公网" |
| R-9 | 误删考试导致数据丢失 | 历史记录损失 | 删除二次确认 + 删除前自动快照 + `audit_log` 记录 + 每日备份可回溯 |
| R-10 | 目标院校录取线数据过期或口径混淆 | 差距判断失真 | 录取线存"当年总分口径满分"字段，跨口径自动折算；数据可由用户维护；页面标注数据年度 |
| R-11 | 范围蔓延（加入错题本、社交等） | 拖慢核心交付、抬高资源占用 | 严格遵循产品文档 1.4 边界；新增需求走"待确认事项"流程，不直接进开发 |
